# SMTP 465 Configuration and Testing Design

## Goal

Configure the existing account email flow for the user's 163 mailbox using SMTP on port 465 with implicit TLS, and add focused automated tests for the transport configuration. Do not use a real mailbox or credential in automated tests.

## Existing behavior

- `api/Accounts.cs` sends verification and password-reset messages with `System.Net.Mail.SmtpClient`.
- The API's `EnableSsl` setting uses STARTTLS and does not support implicit TLS on port 465.
- `.env.dev` is ignored by Git and is the documented local override for mail settings.
- Existing API integration coverage sends mail through a loopback SMTP capture server; it is not a TLS server and does not exercise real 163 delivery.
- The workspace is not a Git repository, so the design document cannot be committed.

## Proposed design

1. Replace the SMTP transport implementation with MailKit, selecting `SecureSocketOptions.SslOnConnect` for port 465 with TLS enabled. Require TLS in production; allow explicit non-TLS mode only for a loopback host in Development so the existing SMTP capture remains usable. Use STARTTLS for TLS-enabled non-465 SMTP ports.
2. Isolate transport configuration and sending behind a small account-mail service. The service receives configuration and message details; it does not change token generation, hashing, expiry, single-use consumption, or account-flow semantics.
3. Add a .NET unit-test project to verify the port/security-mode mapping and relevant configuration behavior without network access or real credentials. Preserve the existing loopback API integration test for end-to-end account email flows.
4. Update `.env.dev.example` and relevant README guidance for 163 SMTP on port 465. Create a local ignored `.env.dev` containing the non-secret host, port, TLS, username, and sender settings only; leave `Mail__Password` empty for the user to fill locally after rotating the exposed authorization code.
5. Do not print, commit, test with, or otherwise reuse the credential pasted in chat. The user must revoke it and generate a new authorization code before actual delivery testing.

## Error handling and security

- Keep the existing explicit API failure behavior when SMTP delivery fails and avoid logging configuration values, message tokens, or credentials.
- Use the configured username/password pair only for SMTP authentication.
- No test contacts `smtp.163.com`; no test stores or echoes a real secret.
- A successful unit or loopback test does not prove real mailbox delivery. Actual delivery is a separate manual verification after credential rotation.

## Acceptance criteria

- The API builds with the new SMTP transport.
- Unit tests prove port 465 maps to implicit TLS and do not perform network I/O.
- Existing account integration tests continue to pass against loopback SMTP capture.
- The local environment file is ignored by Git and contains no password value.
- Documentation explains where the user can enter the newly generated local authorization code and distinguishes automated tests from real SMTP acceptance.
